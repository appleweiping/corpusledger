# CorpusLedger 0.2.0

Released 2026-08-31.

CorpusLedger 0.2 makes the default JSONL snapshot path raw-record streaming, adds explicit reader
extensions and detached Ed25519 signatures, and hardens canonicalization and filesystem boundaries
without changing the version-1 manifest or hash contracts.

## Highlights

- Default JSONL snapshotting derives hashes, schema information, and privacy findings one raw
  record at a time. Incremental canonical sequence hashing preserves the v0.1 results for both
  supported hash algorithms and list policies.
- A typed `ReaderAdapter` protocol and explicitly selected `corpusledger.readers` entry points add
  file-format support. Manifests record strict adapter name/version metadata so verification can
  require the same reader implementation.
- Optional detached Ed25519 envelopes authenticate the exact manifest bytes against a separately
  trusted public key. Encrypted PEM private keys can receive their password through a named
  environment variable; malformed envelopes, changed bytes, wrong keys, and bad passwords fail
  through explicit error paths.
- Canonical input validation now rejects unpaired Unicode surrogates, binary64 overflow,
  resource-exhausting integers, and invalid reader identities. CLI output checks also reject
  hard-link aliases of protected inputs, and Markdown report boundaries escape untrusted text.
- A deterministic JSONL generator and checked end-to-end snapshot benchmark document the workload,
  retained manifest state, and raw-payload streaming boundary.

## Compatibility and migration

Existing `corpusledger/1` manifests need no migration. Their sha256/blake2b and preserve/sort-list
hashes remain under the historical contract, and a load/save round trip does not add
`reader_metadata`. The field is an optional top-level extension used only when an adapter created
the manifest. Such a manifest must be rebuilt or verified with the recorded adapter name and
version.

Signing is an optional extra and does not alter the manifest format. The signature envelope is a
separate artifact over the exact manifest-file bytes.

## Verification

The release candidate passed 93 tests with 94.39% branch coverage. Ruff, strict mypy, source/wheel
builds, and an isolated wheel smoke test passed. Golden compatibility fixtures cover both v0.1
hash algorithms and list policies; tests also exercise streaming, adapter contracts, signatures,
tampering, JSON numeric/Unicode limits, and hard-linked paths.

## Known boundaries

- Raw JSONL record bodies are not retained after processing, but a complete manifest necessarily
  retains per-record entries plus unique IDs, schema paths, and findings. Total memory is therefore
  not constant in corpus size. The largest record and longest physical line also bound the raw
  payload working set.
- Standard `.json` arrays are materialized. `list_strategy="sort"` retains canonical sequence
  members to preserve v0.1 global sorting; the default `preserve` policy is the streaming path.
- Reader entry points are opt-in trusted Python code executed in process, not a sandbox.
- A detached signature provides authenticity only when the verifier receives the expected public
  key through a trusted channel. The top-level absolute source path intentionally makes complete
  manifest bytes location-specific even though content hashes are location-independent.
